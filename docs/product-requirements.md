# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称
**SwipeMatch** - 社内AIイベント ロゴ投票アプリ

### プロダクトコンセプト
- **スワイプで迷わない1次選考**: 100〜200枚規模の作品でも、Tinder風スワイプUIで直感的にサクサク選べ、表示順による有利不利をなくす
- **心理的ハードルを下げる投票体験**: 「Dislike」ではなく「キープして温存する」という前向きな操作に置き換え、同僚の作品を無下に扱う罪悪感を解消する
- **認証なしで繰り返し使い回せる運営**: 複雑な認証機構を持たず、管理者が「コンペ」を題名だけ決めて開催すれば、都度ゼロから構築し直さずにイベントのたびに専用URLで展開できる

### プロダクトビジョン
社内AIイベントの「ロゴ作成大会」を、参加者全員が気軽に参加でき、かつ公平感のある投票で盛り上がるアイスブレイクにする。大人数・大量の作品があっても迷わず選考できるスワイプ体験と、匿名性に配慮した投票フローにより、参加のハードルを下げる。運営は管理者ダッシュボードで「コンペ」を開催するだけで、開催のたびに独立した専用URL・投稿データ・フェーズ管理を使い回せる。イベント当日は結果発表画面をスクリーンに映し、ランキングをアニメーションで演出しながら投稿者の名前とともに優勝作品を称える瞬間を盛り上げる。

### 目的
- 社内イベントのアイスブレイクとして、参加者が気軽に楽しめる投票体験を提供する
- 100〜200枚規模の作品数でも、表示順による有利不利をなくし、公平な選考を実現する
- 同僚の作品への遠慮なく投票できる、心理的ハードルの低いUXを提供する
- 認証機構を作り込まず、開発期間を最小限に抑えてイベント当日までに間に合わせる
- 同じ仕組みを使い回し、社内で繰り返し開催されるロゴ作成大会のたびにアプリを作り直さずに済むようにする

## ターゲットユーザー

### プライマリーペルソナ: 佐藤花子（28歳、営業部）
- 社内AIイベントに参加する一般社員。普段は業務アプリ以外のツールに慣れていない
- スマートフォンのブラウザからアクセスし、休憩時間や移動中の隙間時間で投稿・投票を行う
- ロゴを1〜2点投稿し、投票フェーズでは同僚の作品を気軽に眺めながらキープ／次への仕分けを楽しみたい
- 同僚の作品を露骨に「イマイチ」と評価することに抵抗があり、匿名かつポジティブな操作で選考したい
- 操作説明を読み込む時間はなく、直感的に迷わず使えることを期待している

### セカンダリーペルソナ: 山田健太（32歳、イベント運営担当）
- 社内AIイベントの企画・進行を担当し、当日の司会も務める。四半期ごとなど、同じ形式のロゴ作成大会を繰り返し企画することがある
- イベントのたびに管理者ダッシュボードでコンペの題名を決めて開催し、発行された専用URLを参加者に案内する
- 投稿受付の締切、投票の開始・終了などフェーズの切り替えを管理する
- イベント終盤で結果発表画面をスクリーンに映し、ランキングと投稿者名を読み上げて優勝者を発表する
- 事前にランキングや投稿者名が参加者に漏れないよう、結果画面へのアクセスを制御したい

## 成功指標(KPI)

### プライマリーKPI
- 作品投稿数: 参加者200名中50件以上の投稿（投稿フェーズ終了時点）
- 決選投票完了率: 投票フェーズに参加した人のうち80%以上が決選投票まで完了する（1次選考で離脱しない）
- イベント当日のシステムダウンタイム: ゼロ（投稿・投票・結果発表の全フェーズを通して）

### セカンダリーKPI
- 1次選考のゼロキープ離脱率: キープされた作品が0件で決選投票に進めずに離脱するユーザーの割合を5%未満に抑える
- 結果発表画面への事前アクセス（パスワード未入力での閲覧）: ゼロ件
- コンペ作成〜専用URL発行までの操作時間: 1分以内（管理者がコンペ名を入力し「開催」を押してからQRコードが表示されるまで）

## 機能要件

### コア機能(MVP)

#### コンペ管理（開催・専用URL発行）

**ユーザーストーリー**:
運営担当として、イベントのたびにアプリを作り直さず使い回すために、コンペの題名を決めて開催し、そのコンペ専用のURLを発行できる機能が欲しい

**受け入れ条件**:
- [ ] 管理者ダッシュボードでコンペの題名を入力し、「開催」ボタンで新しいコンペを作成できる
- [ ] コンペを開催すると、ランダムな短い識別子を含む専用URL（例: `/c/x7k2p9`）が自動発行され、そのままQRコードとして表示される
- [ ] 常に1つのコンペのみが「開催中」の状態になる。新しいコンペを開催すると、それまで開催中だったコンペは自動的にクローズされる
- [ ] クローズされたコンペの投稿・投票データはそのまま保持され、管理者は後から結果を確認できる
- [ ] 管理者ダッシュボードから、過去に開催したコンペの一覧（題名・開催日・状態）を確認できる
- [ ] 開催中のコンペが無い状態でトップURLにアクセスした参加者には、その旨の案内を表示する

**優先度**: P0(必須)

#### フェーズ管理（投稿フェーズ／投票フェーズ）

**ユーザーストーリー**:
運営担当として、投稿受付中の作品が投票側に混在しないように、投稿締切後に投票フェーズへ切り替えるための機能が欲しい

**受け入れ条件**:
- [ ] 現在のフェーズ（投稿中／投票中）を、開催中のコンペ単位で切り替えられる（他のコンペのフェーズには影響しない）
- [ ] 投稿フェーズ中は「投票へ進む」ボタンを非活性化し、「準備中」ラベルを表示する
- [ ] 投票フェーズ中は新規投稿を受け付けない

**優先度**: P0(必須)

#### 画像アップロード機能

**ユーザーストーリー**:
参加者として、自分の作ったロゴを気軽に投稿するために、画像・投稿者名・一口メモを入力する投稿フォームが欲しい

**受け入れ条件**:
- [ ] ロゴ画像・投稿者名・一口メモをすべて必須項目として入力できる
- [ ] 1人が複数点のロゴを投稿できる
- [ ] 投稿者名は運営の管理者画面でのみ表示され、投票画面では表示されない（匿名化される）
- [ ] 画像はサイズ上限10MB・許可形式（jpg/png/heic/webp）を超える場合はアップロード前にエラーを表示する

**優先度**: P0(必須)

#### スワイプ式1次選考（Tinder風UI）

**ユーザーストーリー**:
参加者として、大量の作品の中から気軽に好みの作品を絞り込むために、直感的なスワイプ操作でキープ／次へを仕分けできる機能が欲しい

**受け入れ条件**:
- [ ] 投稿された画像と一口メモが、ユーザーごとにランダムな順番で1枚ずつ表示される
- [ ] 右スワイプ（キープ）／左スワイプ（次へ）の操作で仕分けできる
- [ ] 選考状態はブラウザのlocalStorageに保持され、決選投票に進む前提として最低1枚のキープを必須とする
- [ ] ブラウザを閉じる・キャッシュを削除すると選考状態はリセットされ、最初からやり直しになる（MVPでは許容する）
- [ ] 現在までの進捗（残り枚数）がプログレスバー等で表示される
- [ ] キープ／次への操作時に効果音またはアニメーションでフィードバックが返る

**優先度**: P0(必須)

#### 決選投票

**ユーザーストーリー**:
参加者として、1次選考でキープした作品の中から本当に優勝にふさわしいと思う作品を選ぶために、グリッド形式で一覧を見ながら投票できる機能が欲しい

**受け入れ条件**:
- [ ] 1次選考でキープした画像のみがグリッド形式で一覧表示される
- [ ] 上位3つまでを選択して投票できる（3件選択済みの状態で4つ目をタップした場合は選択されず、上限に達している旨を軽くフィードバックする）
- [ ] 自分が投稿した作品への投票（自己投票）も許可される
- [ ] 投票完了後、同一端末から再度投票フェーズに入っても再投票できない（匿名IDベースの制御）

**優先度**: P0(必須)

#### 匿名IDによる多重投票防止

**ユーザーストーリー**:
運営担当として、認証なしでも最低限の公平性を保つために、同一端末からの重複投票を防ぐ仕組みが欲しい

**受け入れ条件**:
- [ ] 初回アクセス時にCookieまたはlocalStorageベースの匿名IDが発行される
- [ ] 決選投票は同一匿名ID・同一コンペにつき最大3票までに制限される（別のコンペでは独立してカウントされ、あらためて投票できる）
- [ ] ランオフ投票も同一匿名ID・同一コンペ・同一ラウンドにつき1票までに制限される（ラウンドが変わればあらためて投票できる）
- [ ] 匿名IDと投稿者の実名は紐付けない（あくまで多重投票防止のみに使用）

**優先度**: P0(必須)

#### 結果発表（管理者画面）

**ユーザーストーリー**:
運営担当として、イベント当日に優勝者を発表するために、得票数ランキングと投稿者名を確認できる管理者専用画面が欲しい

**受け入れ条件**:
- [ ] 得票数の多い順にランキング形式で画像・一口メモ・投稿者名（本名）が表示される
- [ ] 得票数が同数の場合、対象作品にランオフ対象である旨が表示される（再投票の仕組みは「ランオフ（同数得票時の再投票）」を参照）
- [ ] 管理者画面には簡易パスワードが設定されており、パスワードを知らない参加者はアクセスできない
- [ ] スクリーン投影を想定した見やすいレイアウトで表示される
- [ ] 管理者が「発表開始」を操作すると、下位から上位の順にランキングがスライドイン表示され、得票数がカウントアップするアニメーションで結果を演出できる

**優先度**: P0(必須)

#### ランオフ（同数得票時の再投票）

**ユーザーストーリー**:
運営担当として、決選投票で得票数が同数になった場合でも公平に優勝を確定させるために、対象作品同士で再投票を行い、それでも決着しない場合は同率優勝として確定できる機能が欲しい

**受け入れ条件**:
- [ ] 決選投票の結果、順位の境界（特に1位）で得票数が同数の場合、対象作品にランオフ対象である旨が表示される
- [ ] 運営が「ランオフを開始」を操作すると、対象作品のみを表示するランオフ投票画面が参加者に公開される
- [ ] ランオフ投票では対象作品から1つだけ選んで投票できる（通常決選投票の「最大3つまで」とは異なる）
- [ ] ランオフに参加できるのは、通常の決選投票を行った参加者のみに限られる
- [ ] 運営が投票を締め切ると、対象作品の得票数を集計し、同着が解消したかどうかを確認できる
- [ ] 締め切ってもなお同着が続く場合、運営は「再投票」（同じ仕組みでもう一度ランオフを行う）または「同率優勝」（それ以上投票を行わず同率1位として確定する）を選択できる
- [ ] 同率優勝として確定した作品は、結果発表画面で同率であることが分かるように表示される

**優先度**: P0(必須)

#### QRコード配布

**ユーザーストーリー**:
運営担当として、会場で参加者にコンペ専用URLへのアクセスを案内するために、QRコードを表示・印刷できる機能が欲しい

**受け入れ条件**:
- [ ] コンペを開催した直後に、管理者ダッシュボードでそのコンペ専用URLのQRコードを表示できる

**優先度**: P1(重要)

#### 結果ランキングのCSVエクスポート

**ユーザーストーリー**:
運営担当として、Supabase無料枠に自動バックアップがないことによるデータ喪失リスクに備えるために、結果発表フェーズの得票ランキングをCSVでエクスポートできる機能が欲しい

**受け入れ条件**:
- [ ] 結果発表フェーズにおいて、管理者ダッシュボードからランキング（画像URL・投稿者名・一口メモ・得票数・順位）をCSVでダウンロードできる

**優先度**: P1(重要)

### 将来的な機能(Post-MVP)

#### 本格的なユーザー認証

社員アカウントとの連携など、より確実な本人確認を伴う認証機構。

**優先度**: P2(できれば)

#### 1次選考状態のサーバー保存・複数端末間同期

localStorageではなくサーバー側にキープ状態を保存し、端末をまたいだ再開を可能にする。

**優先度**: P2(できれば)

#### 投稿の編集・削除機能

投稿者自身が、投稿した画像やメモを後から編集・削除できる機能。

**優先度**: P2(できれば)

#### イベント後のデータ自動削除ポリシー

一定期間経過後に投稿データ・投票データを自動削除する仕組み。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス
- スワイプ画面での画像切り替え: 操作から200ms以内に次の画像を表示
- 想定同時アクセス200名程度において、画像アップロード・投票操作が体感的な遅延なく完了する

### ユーザビリティ
- 初めて訪れた参加者が、説明を読まずに30秒以内にスワイプ操作を開始できる
- スマートフォンでの片手操作を前提としたUIサイズ・配置にする

### 信頼性
- イベント当日（投稿フェーズ・投票フェーズ・結果発表）を通じてダウンタイムゼロ
- 通常運用時の投票データ・投稿データの損失ゼロ（Supabaseの永続ストレージに保存）。ただしSupabase無料枠には自動バックアップ機能がないため、結果発表フェーズ移行時点で運営が得票ランキングをエクスポートできるようにし、大規模障害時のデータ喪失リスクに備える（詳細は`architecture.md`のバックアップ戦略を参照）

### セキュリティ
- 管理者（結果発表）画面は簡易パスワードで保護し、URLを知っているだけではアクセスできないようにする
- 投稿者名は投票画面では非表示とし、管理者画面のみで開示する
- 匿名IDは個人を特定できる情報と紐付けない

### スケーラビリティ
- 想定利用規模はコンペ1回あたり最大200名、作品数100〜200点程度で、Supabase無料枠の範囲内で運用できることを前提とする
- 同じ仕組みを繰り返し使い回して複数回コンペを開催することは想定するが、複数のコンペを同時並行で運用すること（真のマルチテナント化）や、大規模なトラフィックへの対応はスコープ外とする
- 過去に開催したコンペのデータは自動削除せず保持する。長期的な件数増加によるSupabase無料枠の容量超過リスクは運用時の課題として認識し、必要に応じて古いコンペのデータを手動で整理する運用を想定する

## スコープ外

明示的にスコープ外とする項目:
- 本格的なユーザー認証・SSO連携
- 1次選考状態のサーバー保存・複数端末間の再開機能
- 投稿の編集・削除機能
- イベント終了後のデータ自動削除・保持ポリシーの運用
- 複数コンペの同時並行開催（常に1つのみが「開催中」となる。過去コンペの閲覧は可能）
- コンペごとに異なる管理者パスワードを設定する機能（管理者認証は全コンペ共通のまま）
- コンペURLのカスタムスラッグ指定（ランダムな短い識別子の自動発行のみ）
- 参加者が自分の端末で結果発表画面を直接閲覧する機能（結果発表は引き続き管理者ダッシュボードからのスクリーン投影を前提とする）
- 大量アクセス（数千人規模）を想定したスケーラビリティ対応
