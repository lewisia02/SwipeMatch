# Steering スキル

ステアリングファイル（`.steering/`）による作業計画・実装・振り返りを支援し、tasklist.md の進捗管理を確実に行うスキルです。

## スキルの目的

- ステアリングファイル（requirements.md, design.md, tasklist.md）の作成
- tasklist.md に基づく段階的な実装と、リアルタイムな進捗記録
- 実装完了後の振り返り記録

## 3つのモード

| モード | タイミング | 内容 |
| --- | --- | --- |
| モード1 | 作業計画時 | ステアリングファイルを作成する |
| モード2 | 実装時 | tasklist.md に従い実装し、進捗を更新する |
| モード3 | 検証時 | 振り返りを記録する |

## 最重要原則: 進捗は tasklist.md に残す

- **tasklist.md が正式な記録**。TodoWrite は補助的な揮発メモ（ユーザーには見えない）。
- タスクの開始・完了ごとに、その都度 Edit で tasklist.md を更新する（まとめて更新しない）。
- 常に「ユーザーが tasklist.md を見て進捗が分かるか？」を自問する。

## タスク完全完了の原則

**全タスクが `[x]` になるまで作業を継続する。** 未完了（`[ ]`）を残したまま振り返りを書かない。

- 「時間の都合」「難しい」「後回し」などを理由にスキップしない。
- タスクが大きすぎる場合 → サブタスクに分割し tasklist.md に追記して1つずつ完了させる。
- **スキップが許可されるのは技術的理由のみ**（実装方針・アーキテクチャ・依存関係の変更により不要になった場合）。
  - スキップ時は理由を明記する: `- [x] ~~タスク名~~（実装方針変更により不要: 具体的な理由）`
  - あわせて振り返りセクションにも変更理由を記録する。

---

## モード1: ステアリングファイル作成

1. **ディレクトリ作成**: 現在日付で `.steering/[YYYYMMDD]-[機能名]/` を作成する。
2. **永続ドキュメントの確認**: `docs/` 配下（product-requirements / functional-design / architecture / repository-structure / development-guidelines）を読み、プロジェクトの方針を把握する。
3. **テンプレートから3ファイルを作成**（プレースホルダーを具体化する）:
   - `templates/requirements.md` → `.steering/[日付]-[機能名]/requirements.md`
   - `templates/design.md` → `.steering/[日付]-[機能名]/design.md`
   - `templates/tasklist.md` → `.steering/[日付]-[機能名]/tasklist.md`
4. **tasklist.md の詳細化**: requirements.md と design.md に基づき、各フェーズのタスク・サブタスク・実装順序を具体化する。**実装可能なタスクのみ**を列挙する（「将来やるかも」「検討中」は含めない）。

---

## モード2: 実装（最重要）

### 実装フロー

1. **tasklist.md を読み込み**、次の未完了タスク（`[ ]`）を特定する。
2. **TodoWrite でタスクリストを作成**する（補助メモ。正式な記録は tasklist.md）。
3. **各タスクで以下を繰り返す**:
   1. 着手するタスクを TodoWrite で `in_progress` にする。
   2. 開発ガイドライン（`docs/development-guidelines.md`）に従って実装する。
   3. 完了したら **Edit で tasklist.md の該当行を `[ ]` → `[x]` に更新**する（サブタスクも個別に更新）。

      ```
      old_string: "- [ ] StorageServiceを実装"
      new_string: "- [x] StorageServiceを実装"
      ```

   4. TodoWrite でも `completed` に更新する。
4. **フェーズ完了ごと**に tasklist.md を読み直し、漏れがないか確認してユーザーに報告する。

### 全タスク完了チェック（振り返り前に必須）

tasklist.md を読み込み、`[ ]` が1つも残っていないことを確認する。残っている場合は:

- 実装する、またはサブタスクに分割して完了させる。
- 技術的理由で不要になった場合のみ、理由を明記してスキップする（上記「タスク完全完了の原則」を参照）。

### セルフチェック（5タスクごと）

- [ ] tasklist.md を直近5タスク以内に更新したか？
- [ ] 進捗がドキュメントに反映されているか？（Read で確認）

---

## モード3: 振り返り

1. tasklist.md を読み込む。
2. 「実装後の振り返り」セクションを Edit で更新する:
   - 実装完了日
   - 計画と実績の差分
   - 学んだこと（技術的な学び、プロセス上の改善点）
   - 次回への改善提案
3. ユーザーに報告する。

---

## トラブルシューティング

**更新を忘れた場合**: すぐに tasklist.md を読み込み、完了済みタスクをすべて `[x]` に更新する。ユーザーに遅延を報告し、以降はその都度更新する。

**計画と実装が乖離した場合**: 該当タスクに注釈を追加する（`- [x] タスク名（実装方法を変更: 理由）`）。必要ならタスクを追記し、変更が大きければ design.md も更新する。

---

## このスキルの効果

- tasklist.md が常に最新の進捗を反映し、ユーザーが一目で把握できる。
- ドキュメントと実装の乖離がなくなり、振り返りと次回の改善につながる。
- プロジェクト履歴として価値のある記録が残る。
